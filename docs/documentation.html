1. What this project is

You paste a long link and get back a short one, like https://url-shortener.2wf0w2.workers.dev/100. Anyone visiting the short link is redirected to the original, and each visit is counted - approximately, since bots and prefetchers trigger visits too - so you can see click analytics per link.

Why build it: it is a small system that still forces the classic system-design decisions - how short codes are generated, 301 vs 302 redirects, the SQL schema and indexes, caching for hot links, abuse protection, and analytics. These are exactly the questions interviewers ask about shorteners.

A1. What happens when you open a link

Everything in this project is built on one everyday action: opening a URL in a browser. So the first chapter is what actually happens in that moment.

A URL is an address with parts

Take https://url-shortener.2wf0w2.workers.dev/107 . It has four parts. The scheme, https://, says which set of rules (protocol) the browser should speak: HTTP, the rules for transferring web content, with an S for the encrypted version nobody can read in transit. The host, url-shortener.2wf0w2.workers.dev, names the computer to talk to. Computers are really found by numeric IP addresses like 192.0.2.1, so a worldwide phone book called DNS (Domain Name System) translates the host name into one. The path, /107, says which thing on that computer you want. A URL can also carry a query after a ? for extra options; this project never needs one.

The browser sends a request, the server sends a response

Once the browser has the IP address, it opens a connection and sends an HTTP request: a plain-text message with a method (a verb like GET for "give me" or POST for "here is new data"), the path, and headers - extra lines of metadata such as what kind of answer the browser prefers, or a sign-in token. The server, a program running on the computer at that address, reads the request and answers with an HTTP response: a status code (a number saying how it went), its own headers, and usually a body - the actual content, like a web page or some data.

Status codes you will meet in this project

• 200 OK - the request worked and the body carries the answer.

• 201 Created - like 200, but specifically "your new thing was made". Creating a short link answers 201.

• 301 Moved Permanently and 302 Found - redirects: "what you want is at another address, go there". The difference matters so much that chapter A10 is all about it.

• 400 Bad Request - you sent something the server cannot accept, like a URL with no http:// in front.

• 401 Unauthorized - you need to sign in first.

• 403 Forbidden - signing in would not help or this is not yours. Reading another person's private link stats answers 403.

• 404 Not Found - nothing exists at that path, like a short code nobody created.

• 409 Conflict - your request clashes with existing data, like a custom code someone already took.

• 410 Gone - it existed, but it is gone for good. Expired links answer 410.

• 429 Too Many Requests - you are being rate limited (chapter A13).

• 500 Internal Server Error - something broke on the server's side.

Two response headers matter as much as the code. content-type tells the browser what the body is (text/html for a page, application/json for data), and Location is what a redirect uses to say where to go next.

That is the whole foundation. Every feature of the shortener - creating links, redirecting, stats, sign-in - is just the browser and our server exchanging these little messages.

A2. Servers, hosting and "the edge"

What a server really is

A server is not special hardware; it is a program that waits for HTTP requests and answers them. In the classic setup you write a server program (in Node.js with a framework like Express, say), rent a virtual machine from a hosting company, and leave your program running on it day and night. You pay for the machine even when nobody visits, and if it crashes your site is down until you restart it. Many free tiers make the machine sleep when idle, so the first visitor after a quiet spell waits several seconds while it wakes up.

Serverless and Cloudflare Workers

This project instead runs on Cloudflare Workers, a serverless platform. The name is a fib - there are still servers - but you never rent or manage one. You upload a single JavaScript file containing a function called fetch(request), and Cloudflare copies it to hundreds of its data centers around the world. These locations are called POPs (points of presence) or "the edge", because they sit at the edge of Cloudflare's network, physically close to users. When a request arrives, Cloudflare runs your code in whichever data center is nearest the visitor, and the free tier (no credit card) covers our traffic levels easily. There is no machine to keep alive and no sleeping server.

Why that matters specifically for a URL shortener: the redirect is the hot path, the one route that must answer as fast as possible and will be hit vastly more often than everything else. Running it in 300 cities beats running it on one rented box in one city.

Our whole server is one file, worker/index.js, about 350 lines. Its fetch function is the front door: every request to our site enters there, and it decides which handler runs. You will read it piece by piece in chapters A8 and A9. The same provider also gives us the database (chapter A4), so code and data live on the same network.

A3. APIs and JSON - how programs talk

An API (Application Programming Interface) is the menu of requests a server accepts, written down so that programs - not humans - can order from it. A website's pages are for humans; its API is for other software, including our own frontend. Our API has four endpoints (menu items): POST /api/links creates a link, GET /api/links/:code/stats reads analytics, GET /api/links/mine lists your own links, DELETE /api/links/:code removes one. The :code part is a placeholder meaning "whatever code goes here", so /api/links/107/stats asks for the stats of link 107.

API answers need a data format both sides understand, and the web's standard is JSON (JavaScript Object Notation). It looks like this: {"code": "107", "total_clicks": 5, "by_day": [{"day": "2026-11-09", "clicks": 5}]}. The rules are simple: curly braces hold an object of "name": value pairs, square brackets hold a list, strings always use double quotes, and values can be strings, numbers, true/false, null, lists or more objects. That is the entire syntax - you can already read every API answer in this project.

In the browser, JavaScript calls an API with the built-in fetch function. When you click "Shorten" in the demo, your click literally runs fetch("/api/links", {method: "POST", body: JSON.stringify({url: "..."})}); the answer comes back as a Response whose .json() method parses the JSON body. Keep this in mind: the visible website and the API are two layers, and the website is only a friendly face over the same endpoints anyone could call.

A4. Databases from zero - where the links live

Tables, rows, columns

A database is a program whose only job is storing data reliably and finding it again fast. The kind used here is a relational database, which organises data into tables. A table is like a spreadsheet: each column is a field with a name and a type, and each row is one record. Our links table has one row per short link - its id, code, long_url, created_at and expires_at - and the clicks table has one row per visit to a short link.

SQL - the language you talk to it with

You command the database in SQL (Structured Query Language). Four verbs cover this entire project: INSERT adds a row, SELECT reads rows, UPDATE changes rows, DELETE removes rows. Read this real line from the project: SELECT code, long_url FROM links WHERE code = '107' - "from the links table, give me the code and long_url of the row whose code is 107".

In the code you will see a ? where values go, like WHERE code = ? . That is a placeholder: the real value is attached separately, which is called binding. Besides being tidy, placeholders are the defence against SQL injection - the classic attack where a visitor types SQL commands into an input hoping the database runs them. With binding, the input is always treated as data, never as a command.

Three constraints from our schema do real work. PRIMARY KEY marks the column that identifies each row, and AUTOINCREMENT means the database itself assigns ids 1, 2, 3... and never repeats one. UNIQUE on code means the database refuses to store two rows with the same code - this is the real guard behind custom codes. And CREATE INDEX on (link_code, clicked_at) keeps a sorted lookup structure so counting a link's clicks stays fast even with millions of rows; without an index, the database would have to read the whole table every time.

SQLite, D1 and migrations

SQLite is the most deployed database in the world: a complete SQL database that lives in a single file, famous for reliability. Cloudflare D1 is SQLite offered as a managed service attached to our Worker - same SQL, but Cloudflare hosts it, and our code reaches it through a binding (a configured connection) named DB in wrangler.toml. Every query in the project has the same shape: env.DB.prepare("SELECT ...").bind(code).first() - prepare the statement, bind the values, run it.

The schema lives in files called migrations: numbered SQL scripts that are applied in order and never edited afterwards. 0001 created the tables (schema.sql), 0002 added the expires_at column for expiring links, 0003 added owner_id for accounts. If the schema changes again, we add migration 0004; we never rewrite the old ones, because the deployed database already ran them. This is how real teams evolve databases safely.

One deliberate trick in the schema: the line INSERT OR IGNORE INTO sqlite_sequence ... 3843 starts the automatic ids at 3844. Chapter A7 explains why - it makes the very first short code come out as "100" instead of "1".

A5. The frontend - what you see and click

HTML, CSS and JavaScript

Every web page is built from three languages. HTML (HyperText Markup Language) describes the structure: here is a heading, here is an input box, here is a button. CSS (Cascading Style Sheets) describes the look: colors, sizes, spacing - ours is hand-written in styles.css so every line is readable. JavaScript is the behaviour: what happens when you click Shorten.

React and components

Writing raw JavaScript that pokes at the HTML directly gets tangled fast, so the frontend uses React, the most popular UI library. React's idea is to build the page from components - small functions that return a description of a piece of UI - and to keep the changing data in state. When state changes, React re-runs the component function, compares the new description with what is actually on screen, and updates only the parts that differ - that comparison step is called reconciliation. The UI lives in client/src/App.jsx (about 330 lines): App is the root component, composed of smaller ones - the deep-dive chapter right after this one names and reads each piece.

JSX is React's syntax that lets you write HTML-looking tags inside JavaScript, like <button onClick={shorten}>Shorten</button>, where the braces embed real JavaScript values. Browsers cannot run JSX, so a build tool converts it - that is Vite's job. While you work, Vite runs a fast development server; npm run build then produces the final static files (plain HTML, CSS and JavaScript) into the dist/ folder. Static means fixed files with no server-side logic: Cloudflare serves them straight from the edge, and anything that is not a file falls through to our Worker code.

localStorage and QR codes

Two browser features finish the picture. localStorage is a small key-value store inside your browser that survives closing the tab: the app saves the codes you created there, so Your links can show your history without any account. Its limit is exactly why accounts were worth adding in stage 2: localStorage lives in one browser on one device, so your list did not follow you to your phone. And the QR codes (the scannable square barcodes) are drawn entirely in your browser from the short URL - no external QR service is involved, which is what client-side generation means. (The destination itself was already sent to our server when the link was created; the local part is making the image.)

Frontend deep dive - reading App.jsx piece by piece

Chapter A5 introduced React in the abstract. This chapter reads the actual frontend - client/src/App.jsx, about 330 lines - in small sections, teaching each new idea the moment it appears. After it, you will be able to follow what each part does and try small changes with a good idea of what to expect. It will not make you fluent in React by itself; it will make this codebase yours.

How the page boots: index.html and main.jsx

Open client/index.html: it is almost empty - one <div id="root"></div> and one <script type="module" src="/src/main.jsx">. That is the React pattern: the HTML is a shell with a mounting point, and JavaScript builds everything inside the div. "type=module" means the file may use import statements.

main.jsx does three things. It imports App (the one big component) and styles.css. It reads the Clerk publishable key from import.meta.env.VITE_CLERK_PUBLISHABLE_KEY - Vite replaces import.meta.env.VITE_* names at build time with values from the .env files; the publishable key is public by design, so shipping it inside the built JavaScript is safe. Then createRoot(document.getElementById("root")).render(<ClerkProvider ...><App /></ClerkProvider>) mounts the app: createRoot grabs the div, render draws the component tree into it. ClerkProvider wraps App so every component inside can use Clerk's sign-in powers.

Components and props

App.jsx is five components: App (the page), ShortenForm (the create card), Stats (the analytics card), QrButton and CopyButton. A component is a function whose return value describes UI; using <CopyButton text={...} /> inside another component mounts it there. The values you pass are props - inputs arriving as one object, unpacked with destructuring: function CopyButton({ text }) means "take the text field out of the props object". Destructuring appears everywhere in this file: { onCreated }, { code, onClose }.

State: useState, and why the page updates itself

Plain JavaScript variables do not redraw the page when they change. React's answer is state, made with the useState hook (a hook is a React function whose name starts with "use"; each one adds a power to a component):

const [url, setUrl] = useState("");

Read it: useState("") creates a state box holding ""; it returns a pair - the current value and its setter - and the square brackets destructure the pair into url and setUrl. Calling setUrl("https://...") stores the new value AND tells React to re-run the component function, so the UI re-renders with fresh data. Every changing thing on the page is state: url, customCode, expiresAt, busy, error, created in the form; links, theme, statsFor in App.

The inputs are controlled: <input value={url} onChange={(e) => setUrl(e.target.value)} />. The input shows state, and every keystroke fires onChange, whose event object e carries the typed text at e.target.value, which goes straight back into state. Value flows state -> screen -> state, one loop per keystroke. (e) => setUrl(...) is an arrow function: a compact function - parameters, then =>, then the body.

Forms and events: the submit walkthrough

The form's onSubmit={submit} runs when you click Shorten. submit first calls e.preventDefault() - without it, the browser would reload the page, wiping our state, a real bug beginners meet. Then the whole create flow in miniature - a shortened teaching excerpt with a few fields replaced by ... ; the full runnable original is the submit function in client/src/App.jsx:

setBusy(true);

const res = await authedFetch("/api/links", {

  method: "POST",

  headers: { "content-type": "application/json" },

  body: JSON.stringify({ url, custom_code: customCode || undefined, ... }),

});

const data = await res.json();

if (!res.ok) setError(data.error || "Something went wrong.");

else { setCreated(data); setUrl(""); onCreated(data.code); }

New pieces: customCode || undefined means "the value, or undefined if it is empty" (|| returns the first truthy side; an empty string counts as falsy, undefined makes JSON.stringify drop the field). res.ok is false for any non-2xx status, so one if handles 400, 409 and 429 alike. try/catch/finally wraps it all: catch shows "Network error" if the fetch itself failed, and finally runs setBusy(false) no matter which way it went, so the button never sticks on "Shortening...".

Side effects: useEffect

Some work is not drawing UI: saving the theme, loading stats. React calls these side effects, and they live in useEffect:

useEffect(() => {

  document.documentElement.dataset.theme = theme;

  localStorage.setItem("snip-theme", theme);

}, [theme]);

Read: "after rendering, whenever theme changes, write it to the <html> element (where the CSS reads it) and to localStorage." The array [theme] is the dependency list - the effect re-runs only when a listed value changes. The Stats component uses the same idea with [code, authedFetch]: open stats for a different code and it fetches fresh data automatically.

Custom hooks: useAuthedFetch

A custom hook is just a function that uses hooks - a way to package reusable power. useAuthedFetch wraps the browser's fetch so every request automatically carries the Clerk session token when you are signed in:

const { getToken } = useAuth();

return useCallback(async (path, options = {}) => {

  const token = await getToken().catch(() => null);

  const headers = { ...(options.headers || {}) };

  if (token) headers.authorization = `Bearer ${token}`;

  return fetch(path, { ...options, headers });

}, [getToken]);

useAuth() is Clerk's hook; getToken returns the current session JWT (chapter A14), or null signed out - the .catch(() => null) means a token problem degrades to anonymous rather than breaking the page. The backtick string `Bearer ${token}` is a template literal: backticks let ${...} embed values in text. { ...options, headers } is the spread syntax: copy all of options' fields, then add/override headers. useCallback memoizes the function (returns the same function object between renders until getToken changes) so effects depending on it do not loop.

Rendering lists, conditions and text

Three JSX patterns draw most of the page. Lists: links.map((l) => (<div className="link-row" key={l.code}>...)) - map turns each link object into a piece of UI; key is React's identity hint so updates reorder efficiently. Conditions: {error && <p className="error">{error}</p>} - && returns the right side only if the left is truthy, so the paragraph exists only when there is an error; the ternary busy ? "Shortening..." : "Shorten" picks between two values. And note className, not class: class is a reserved word in JavaScript, so JSX renamed it.

Auth in the UI: Clerk's components

Four Clerk pieces do the visible sign-in work: <SignedOut> and <SignedIn> render their children only in that state (the Delete button sits inside <SignedIn> - but remember from A14 the server re-checks ownership anyway; hiding a button is UX, not security). <SignInButton mode="modal"> opens Clerk's hosted sign-in box; <UserButton> is the avatar menu. In App, const { isSignedIn } = useAuth() switches the link list's data source: signed in, it asks GET /api/links/mine (your server-side list); signed out, it reads codes from localStorage and refetches each code's public stats to rebuild the list.

Persistence without an account

loadCodes shows the pattern: JSON.parse(localStorage.getItem(LS_KEY)) turns the stored text back into an array, || [] falls back to empty, and try/catch survives corrupted data. New codes are unshifted (added to the front) and saved back as JSON text. This is why an anonymous visitor's list survives a refresh but never leaves that browser - and why stage 2 accounts were worth building.

The chart is just CSS

The per-day bars have no chart library: for each day, a <div className="bar"> gets style={{ height: `${(d.clicks / max) * 100}%` }} - its height as a percentage of the busiest day (Math.max(1, ...counts) - the 1 avoids dividing by zero; the spread ... passes the array as separate arguments). style={{ ... }} takes a JavaScript object; CSS-style percentages do the drawing.

Interlude - JavaScript syntax in fifteen minutes (read before A7)

The server and the tests are written in JavaScript, and the next chapters show real code. No prior programming is assumed: this interlude teaches exactly the syntax those snippets use.

Values and names: const and let

A program keeps values (pieces of data) under names. const BASE62 = "0123..." gives the name BASE62 to a string of characters; const means the name will never point at a different value. let s = "" names a value that may change - and it will, one character per loop round. Strings are text in quotes; numbers need no quotes.

Repeating: while

A while loop repeats its block (the lines between { and }) as long as its condition stays true: while (n > 0) means "keep going until n reaches zero". The symbols: > is "greater than", === is "exactly equal" (it also requires the same kind of value, so 1 === "1" is false), and a single = is assignment - giving a name a value. Mixing up = and === is every beginner's first bug.

Remainders and rounding down: % and Math.floor

n % 62 is the remainder of n divided by 62 (13 % 5 is 3); this is how we peel off one base62 digit. Math.floor(n / 62) divides and rounds down to a whole number (Math is a built-in collection of math tools; floor means round down). These two lines are the whole conversion algorithm.

Strings, positions and building text

BASE62[n % 62] picks one character out of the string by position, counting from 0, so BASE62[0] is "0" and BASE62[10] is "a". And s = BASE62[n % 62] + s joins text: the new character goes in front of what we have built so far, because division gives us the last digit first.

Functions: function, return, export

A function is a named recipe. export function toBase62(n) { ... } defines a recipe named toBase62 that takes one input, n. return s ends the recipe and hands s back to whoever called it. export lets other files import and use the function - that is how the tests in chapter A15 can call it directly.

Objects and methods

Most project code handles objects: bundles of named values. Read env.DB.prepare("...").bind(code).first() left to right: from env (the Worker's environment - its configured connections), get DB (the database binding from chapter A4), call its prepare method with the SQL text, then bind with the value, then first to fetch one row. A method is a function attached to an object, called with a dot.

async and await

Some operations take time: reading a database, downloading keys. Marking a function async lets it await such operations - await pauses just that function until the answer arrives, without freezing other requests. Wherever you see await, read it as "wait here for the answer, then continue". Its result is called a Promise: a value you will have soon.

When things go wrong: try, catch, and patterns

Code that can fail - like verifying a token - is wrapped in try { ... } catch { ... }: JavaScript runs the try block, and if anything throws an error it jumps to the catch block instead of crashing. In verifySessionUser, every failure lands in catch and simply returns null, meaning "treat as anonymous". You will also meet regular expressions: compact pattern-matchers for text, written between slashes, like /^[0-9A-Za-z_-]{3,32}$/ - read it as "from start to finish: 3 to 32 characters, each a letter, number, dash or underscore". They look like noise at first; decode them one bracket at a time.

That is every piece of syntax the code chapters use. When a snippet still looks strange, translate it aloud symbol by symbol - code reads much scarier than it is.

A7. Base62 - how a number becomes a short code

Base62 is counting, with more digits. In base 10 you have ten digits (0-9); when you run out you add a column, so 9 becomes 10. In base62 the digits are 0-9, then a-z, then A-Z - 62 symbols - so a three-character code can name 62 x 62 x 62 = 238,328 links, and six characters about 57 billion.

Converting a number to base62 works by repeated division. Take 3844. Dividing by 62 gives 62 remainder 0, so the last digit is digit 0, which is "0". Dividing 62 by 62 gives 1 remainder 0, so the next digit is also "0". Dividing 1 by 62 gives 0 remainder 1, so the first digit is "1". Read the remainders from last to first: "100". That is why the schema seeds ids at 3844: the first link ever created gets the tidy code /100 instead of /1.

The real code, from worker/index.js:

const BASE62 = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

export function toBase62(n) {

  if (n === 0) return "0";

  let s = "";

  while (n > 0) {

    s = BASE62[n % 62] + s;  // n % 62 is the remainder -> the next digit

    n = Math.floor(n / 62);  // integer division -> what is left to convert

  }

  return s;

}

Line by line:

• const BASE62 = ... - the digit alphabet: 62 characters in order; position 0 is "0", position 61 is "Z".

• export function toBase62(n) - define the converter; it takes the number n, and other files may import it.

• if (n === 0) return "0" - the special case: zero converts to the single digit "0".

• let s = "" - start with an empty answer.

• while (n > 0) { ... } - repeat until nothing is left to convert.

• s = BASE62[n % 62] + s - take the remainder (the next digit from the right), look it up in the alphabet, and put it in front of the answer so far.

• n = Math.floor(n / 62) - divide by 62 and round down: what remains to convert.

• return s - hand back the finished code.

Trace it with n = 3844: remainder 0, so digit "0"; s is "0"; n becomes 62. Remainder 0 again; s is "00"; n becomes 1. Remainder 1, digit "1"; s is "100"; n becomes 0 and the loop stops. Answer: "100".

Why derive codes from the database id at all? Because the database guarantees each id is handed out exactly once, so two auto codes can never collide with each other. A custom code can still grab a string a future auto code will want; the retry described two paragraphs down handles that. The honest downside: sequential codes are enumerable, meaning anyone can type /101, /102 and walk through existing links. The alternative, random unguessable codes, needs a generate-check-retry loop on every insert. Both are interview-standard answers. As of 11 Nov 2026 this project implements both (commit 72fcc73, pending your review): sequential stays the default, and an 'Unguessable code' checkbox at creation switches to a random 8-character base62 code drawn from crypto randomness - the operating system's secure random source, not Math.random - with bytes that would favour some characters discarded (rejection sampling), and the same UNIQUE-retry backstop if a collision ever happens.

Custom codes add one wrinkle. Someone could grab "200" as a custom code before the auto ids reach 7688 (the number that converts to "200"). When the id counter eventually gets there, the UPDATE that sets the auto code violates the UNIQUE constraint - so the code catches the error, deletes that row and retries with the next id. You can see that try/catch and retry loop inside createLink.

A8. Walkthrough: creating a link

Now trace a real create through the code. You paste https://example.com/a/very/long/page into the demo and click Shorten. The frontend sends POST /api/links with the JSON body {"url": "https://example.com/a/very/long/page"}. At the bottom of worker/index.js, the fetch function matches method POST and path /api/links and calls createLink. Then, in order:

1. Rate limit first: checkRateLimit counts creates from your IP in the current one-hour window and answers 429 beyond 30 (chapter A13).

2. Who are you: verifySessionUser checks for a sign-in token; with none, ownerId stays null and the link is anonymous (chapter A14).

3. Validation: validateLongUrl rejects anything that is not http/https, is over 2048 characters, points at a private or local network address, or points back at the shortener itself - a short link to itself would redirect forever.

4. Insert: the row goes into links with a random placeholder code, because the real code needs the row id and the id only exists after inserting.

5. Code assignment: the new id is read back, converted with toBase62, and the row is updated to the real code. If a custom code already owns that string, the UNIQUE constraint throws, the row is deleted, and it retries.

6. Answer: 201 with {"code": "108", "short_url": "https://url-shortener.2wf0w2.workers.dev/108", ...}. The frontend shows it and saves the code in localStorage for your list.

Custom codes take the same path with two extra checks: the format rules (3-32 characters of letters, numbers, dash or underscore, and not a reserved word like "api" that would collide with a real route), and a lookup for existing links - a taken code answers 409 Conflict.

A9. Walkthrough: visiting a short link (the hot path)

Someone opens https://url-shortener.2wf0w2.workers.dev/108 . The fetch function sees a GET whose path is not /api/..., treats "108" as a code, and calls redirect. This path is engineered for speed:

1. Edge cache first: caches.default.match asks the local Cloudflare cache "have we answered this code in the last minute?" On a hit, the database is never touched.

2. On a miss: one SQL query fetches the long_url and expiry. An unknown code gets a friendly 404 page; an expired link gets a 410 page.

3. The click is logged with ctx.waitUntil(...): the key trick. waitUntil tells Cloudflare "run this database write after the answer is already on its way", so the visitor's redirect is never delayed by bookkeeping.

4. The answer is a 302 with a Location header set to the long URL and Cache-Control: public, max-age=60, which lets the edge remember it for 60 seconds (chapter A11). Links with an expiry are deliberately not cached, so a cached redirect can never outlive the link itself.

The browser receives the 302, reads Location, and immediately opens the destination. From the visitor's view the shortener is invisible; from ours, every visit passed through and was counted.

A10. Why 302 and not 301

Both codes mean "go to this other address". The difference is memory. A 301 Moved Permanently tells the browser this will always be true - the browser stores it forever and next time skips our server entirely, going straight to the destination. Fast, but we would never see those visits, so analytics would silently undercount. A 302 Found means "go there, but ask me again next time" - every visit passes through us and gets counted. Shorteners that offer analytics need 302 behaviour; the cost is that every redirect needs our server up and answering. Expired links use 410 Gone, which tells browsers and search engines to stop trying altogether.

A11. Caching - remembering answers near the visitor

A cache is a place that keeps a copy of an answer so the next identical question is instant. Cloudflare's edge cache lives in the same data center that runs the Worker. Our redirect stores its 302 there with max-age=60 - a TTL (time to live) of 60 seconds - so for the next minute, repeat visits to that code skip the database. That is what lets a suddenly viral link survive: the hundred-thousandth visit costs the same as the second.

Two honest caveats. Each data center keeps its own cache, so when an owner deletes a link we purge the cached redirect on the location that handled the delete; other locations may keep redirecting until their copy ages out, worst case 60 seconds. And caching is one reason "approximate" is the honest word for web numbers: prefetchers and bots trigger redirects too.

Deleting calls caches.default.delete for the code's URL, and the TTL is the backstop if that best-effort purge fails. Remember the general pattern: caches make reads fast and deletions subtly slow, so everything cached needs an expiry plan.

A12. Analytics - counting clicks per day

Every redirect inserts one row into clicks: the code, the UTC timestamp, the Referer header (the page the visitor came from, often empty; the misspelling is historical and standard), and a coarse country code that Cloudflare attaches to the request. The stats endpoint then answers a set of SQL questions: COUNT(*) for the total; GROUP BY day for the last 30 days, where substr(clicked_at, 1, 10) trims each timestamp to its date; and the 20 most recent rows for the detail list. Since 12 Nov 2026 it also runs GROUP BY referrer and GROUP BY country for the new breakdown bars (section 9.1). The frontend draws the per-day bars in plain CSS - no chart library. Since 11 Nov 2026 it also answers a fourth: GROUP BY hour of day, where substr(clicked_at, 12, 2) trims each timestamp to its UTC hour, returned as 24 by_hour buckets and drawn as a plain-CSS heat strip on the stats view (commit 72fcc73, pending your review).

Timestamps are stored in UTC, the world's shared clock with no time zones. One consequence to know: the by-day chart rolls over at midnight UTC, which is 5:30 AM in India, so "today" on the chart is not quite "today" in IST.

A13. Rate limiting - the brake on abuse

An open create-link endpoint invites abuse: someone could script thousands of junk or malicious links. The brake is a rate limit: at most 30 creates per rolling 60 minutes per IP address. The algorithm is an exact sliding window, sometimes called a rolling log: every create attempt writes one row (ip, created_at) to a create_events table, and the check counts that IP's rows whose created_at falls inside the trailing 60 minutes. ISO-8601 UTC strings sort alphabetically, so a plain >= comparison does the window math. Rows older than a day are pruned on each create, so the log stays small.

Why not the simpler fixed window (one counter per clock hour)? It can burst: thirty creates at 2:59 plus thirty at 3:01 is sixty creates in two minutes, legal across two windows. The rolling window has no boundary, so the burst is gone. Two honest trade-offs: a rejected attempt also writes a row and counts toward the limit (standard limiter behavior - it keeps an abuser limited), and two creates landing in the same instant at the limit's edge can both be rejected (rare, and failing safe). Heavier machinery - the token bucket, and cheaper approximations like the weighted two-window estimate - is the sibling project's subject; its documentation shows this chapter from the other side. (The first version of this project did use a fixed window; the git history shows the swap.)

A14. Sign-in and accounts, from zero

The problem and the classic answer

"Remember who I am" is surprisingly hard, because HTTP is stateless: every request arrives with no memory of any previous one. The classic solution is sessions. After you log in with a password, the server creates a random session id, stores it in its database next to your user id, and sends it to your browser in a cookie - a small piece of data the browser then attaches automatically to every request. Each request, the server looks the session id up. This works well, but it means owning password hashing (passwords are never stored as themselves, only as one-way scrambles), session storage, expiry and password resets: a whole security subsystem.

Tokens and JWT

The newer pattern removes the lookup: instead of a random id to look up, the issuer hands over a signed token that itself states who you are. A JWT (JSON Web Token) is three base64-encoded parts joined by dots: header.payload.signature. The payload is plain JSON anyone can read, for example {"sub": "user_123", "iss": "https://concise-mosquito-7709.clerk.accounts.dev", "exp": 1762700400} - sub is the user id (subject), iss is who issued it, exp is when it expires. If anyone can read it, why trust it? Because of the signature.

Signatures and public keys

Signing uses asymmetric cryptography: a key pair with a private key only the issuer holds and a public key anyone may know. The issuer signs the header plus payload with the private key; anyone holding the public key can verify the signature, but nobody can forge one without the private key. Our Worker downloads Clerk's public keys from a well-known URL called the JWKS (JSON Web Key Set), caches them for an hour, and verifies signatures with the browser-standard WebCrypto API - so no Clerk secret exists anywhere in our system. The algorithm is RS256: RSA signing with SHA-256 hashing. Wherever "RS256" appears in the code or tests, it means exactly that.

What Clerk is, and what the Worker checks

Clerk is a hosted sign-in service: it runs the login form, the email codes and the password rules, and it issues the JWTs. Our app never sees a password - there is no password column anywhere in our database. After sign-in, the frontend sends the token as a header, Authorization: Bearer <token>, on API calls. For each protected request, the Worker's verifySessionUser checks in order: is there a Bearer token; is it unexpired; is the issuer exactly our Clerk instance; does the signature verify against the JWKS. Any failure means "treat the caller as anonymous", not an error - the public features keep working.

Ownership then lives in the database: links created while signed in store your Clerk user id in the owner_id column (migration 0003). Links from before accounts keep owner_id NULL and stay anonymous forever - they are never reassigned, so nobody can claim an old link. Redirects stay public for every link (a short link is meant to be shared). Stats are public for anonymous links, and answer 403 to everyone but the owner on owned links. Delete exists only for owned links: 401 signed out, 403 if it is not yours.

Development versus production

Clerk has two kinds of instance. Ours is a development instance: free, no credit card, capped at 100 users, and it shows a Development mode label in the sign-in box. A production instance requires a custom domain with DNS control (Clerk needs a CNAME record pointing at it), which a free workers.dev address cannot provide. For a learning demo, development mode is the right call - and now you know exactly what a real launch would change.

An automated test is code that runs parts of the project and checks the answers, so a change that breaks something fails loudly instead of surprising users. Ours use the vitest test runner, from the same ecosystem as Vite via npm test. tests/worker.test.mjs checks the pure logic: base62 conversions, the URL validation rules, the custom-code rules, expiry parsing, and the rate-limit window. tests/ownership.test.mjs checks the sign-in rules by building real signed JWTs as fixtures (test data constructed for the test) and confirming a wrong user gets 403, an expired or forged token is treated as anonymous, and a stranger cannot delete.

2. Tech stack - what, why, and the alternatives

Frontend: React + Vite. Same stack as your StudyFlow dashboard, so the code reads familiar; Vite gives a fast dev server and produces a static build the Worker serves directly. The alternative, plain HTML/JS, would work at this size but teaches less component thinking; Next.js adds server-side rendering this project does not need.

API + redirect server: Cloudflare Workers. Free tier with no credit card, and it runs at the edge, so the redirect - the hottest path - answers close to the visitor. The textbook alternative (an Express server plus hosted Postgres) is fine too, but a server process must run somewhere, most free hosting tiers sleep when idle (slow first redirect) or ask for signup details, and the frontend then needs separate static hosting.

Database: Cloudflare D1 (SQLite). The design calls for a real SQL links table with an index on the code; D1 is serverless SQL attached to the Worker with zero servers to manage. Its free tier has daily read/write quotas (millions of reads per day at the time of writing) - generous for a learning project, not unlimited scaling. Postgres would offer richer concurrency features if the project outgrows D1.

Short codes: base62 of the sequential row id. Auto-generated codes never collide with each other, because the database hands out each id exactly once. A custom code can grab a string a future auto code would want; the UNIQUE constraint catches that and the insert is retried with the next id. The real tradeoff: sequential codes are enumerable - someone could walk codes and discover links. Random strings (nanoid-style) are unguessable but need a check-and-retry loop on every insert. Both sides are a classic interview answer - and since 11 Nov 2026 the project implements both (sequential default, random opt-in, commit 72fcc73).

Redirects: 302 Found. A 302 sends the browser through our server on every visit, so clicks stay countable. A 301 is faster for visitors because the browser remembers the redirect and never asks us again - which also means no analytics. Counts are still approximate either way: bots and link prefetchers trigger redirects too.

Analytics: a clicks table, aggregated per day. Every redirect inserts one row asynchronously (the redirect does not wait for the write), and the stats endpoint sums per day. Simple and close to exact; the failure mode is that a failed async write loses a count. At viral scale the usual answer is an in-memory counter (Redis) flushed periodically, which trades exactness for database headroom.

Caching: Cloudflare's edge cache for hot destinations. Repeat lookups for the same code are served from cache for 60 seconds instead of hitting the database; the worker still runs on every request, so clicks keep being logged. Links with an expiry are not cached, because a cached 302 could outlive the link's own expiry.

Styling: hand-written CSS. Worker framework: none. Deliberate learning choices: the API has three routes, so a router library would only hide how request handling works, and plain CSS keeps every line readable.

Auth (stage 2): Clerk, free tier with no credit card - the same provider as the StudyFlow dashboard. The browser signs in with Clerk; the Worker verifies the session token against Clerk's published keys (JWKS), so no password or session data lives in our database. Hand-rolled sessions are the classic alternative and a good interview topic, but duplicating a proven provider adds risk without teaching much new.

3. Architecture and request flows

Create flow: browser -> POST /api/links -> Worker validates the URL and optional custom code and expiry -> row inserted in D1 -> auto code = base62(row id) -> 201 with the short URL -> the browser remembers the code in localStorage so "Your links" can show it later.

Redirect flow (the hot path): visitor -> GET /:code -> edge cache checked -> on a miss, D1 lookup and the result cached -> click logged asynchronously -> 302 Location: long_url. Expired links answer 410, unknown codes 404.

Stats flow: browser -> GET /api/links/:code/stats -> Worker aggregates the clicks table (total, per day for 30 days, per hour of day, referrer and country breakdowns, 20 most recent). Stats are public for anonymous links and private for owned links - the owner's session token is checked server-side -> frontend draws the by-day bar chart in plain CSS.

One Worker serves everything: static frontend files are served first; anything that is not a file goes to the Worker code (the API and the redirect).

7. Security and abuse handling - honest version

  • URL validation: only http/https, max 2048 characters, no private or local network addresses, and never a link pointing back at the shortener itself (redirect loop).
  • Rate limiting: 30 creates per rolling 60 minutes per IP as an exact rolling log (12 Nov 2026) - no boundary bursts. Heavier machinery (token bucket, weighted estimates) is the sibling rate-limiter project.
  • Auto codes are sequential and enumerable by default: someone could walk codes and find links. New links created with the 'Unguessable code' option (11 Nov 2026) avoid this. Stats for anonymous links (including everything created before accounts) are public to anyone with the code; owned links have private stats.
  • The async click log can lose a count if the write fails; counts are approximate, not guaranteed.
  • Cached redirects can keep working for up to 60 seconds after a change or deletion - deleting purges the cache copy on the edge location that handled it, other locations may hold it until expiry; expiring links are excluded from the cache for that reason.
  • Timestamps are UTC, so the by-day chart rolls over at 5:30am IST, not midnight (same known limitation as the dashboard).

8. Interview prep - questions this project answers

  • How do you generate short codes? This project implements both: sequential id encoded in base62 by default (no collisions among auto codes, no retry loop) and an opt-in random 8-character base62 code from crypto randomness (unguessable; check-and-retry backstop). Capacity: 62^6 ~ 57 billion six-character codes; 62^8 ~ 218 trillion for the random option.
  • 301 or 302? 302 keeps every click passing through you, so analytics work; 301 is faster but the browser never asks again. Most shorteners that offer analytics need 302-style behaviour.
  • How do you scale reads? Reads dominate writes enormously, so cache hot codes - here, a 60-second edge cache. The click counter is kept off the hot path via async logging; at bigger scale it moves to an in-memory counter flushed in batches.
  • What breaks? Database down means no redirects for uncached codes; a poisoned cache entry serves a stale destination until TTL; rate limits stop casual abuse, not a determined attacker.

9.1 Analytics: referrers, countries, CSV

Where does a click come from? Two answers, both coarse on purpose. The referrer is the page the visitor was on when they clicked: browsers send it as the Referer header (the misspelling is historical and standard), and it is often empty - privacy modes, apps and typed-in visits send nothing, which we show as "direct". A referrer can also lie, so treat it as an analytics hint, never a security signal. The country is the coarse two-letter code (US, IN) from Cloudflare request metadata, when available; a VPN makes it point at the VPN's country. This click log stores no precise coordinates; it keeps the coarse country value.

The flow: every redirect already stored these two values in the clicks table (chapter A12). The stats endpoint now runs two more GROUP BY queries - GROUP BY referrer and GROUP BY country - and the raw referrer rows are then folded into hosts in JavaScript, because "https://x.com/post/1" and "https://x.com/post/2" are the same source:

function refererHost(referrer) {

  if (!referrer) return "direct";

  try { return new URL(referrer).hostname; } catch { return "other"; }

}

The helper above is the actual worker/index.js function: an empty input returns direct; new URL parses a URL, .hostname selects its host, and catch turns malformed input into other instead of crashing the stats request. The SQL first takes at most 100 distinct raw referrers, ordered by count, then JavaScript combines their host counts, sorts by count (ties alphabetical), and keeps 10 hosts. This is a bounded breakdown, not an exact top-10-host calculation over unlimited distinct URLs: a host spread across many low-count URLs may be undercounted or omitted. Countries use a separate GROUP BY country query capped at 30 groups; missing codes become unknown. The frontend draws ranked CSS bars without a chart library. Why parse hosts in JavaScript? SQLite has no built-in URL parser. Alternatives are storing a normalized host when logging, or returning every raw URL; both change the data or response trade-off. Recent clicks and CSV retain raw referrer strings, so do not publish an anonymous link whose referrer data you need kept private.

CSV export: GET /api/links/:code/clicks.csv answers with the raw click log - newest 5000 rows - as text/csv with a Content-Disposition: attachment header, the standard way to say "download, do not display". CSV (comma-separated values) is a plain-text table format. The writer wraps every field in double quotes and doubles an embedded quote; a missing value becomes an empty field. This keeps commas or quotes in referrers inside one cell. The cap bounds output rows, not query execution cost. Referrers are untrusted text: quoting is not spreadsheet-formula protection. Import as text or inspect with a text editor rather than trusting formulas in downloaded cells.

Privacy is unchanged: breakdowns and CSV follow the stats rule - public for anonymous links, 403 for strangers on owned links (verified live: a stranger's CSV request was refused). Tests: four unit tests for refererHost (empty, with path, subdomain, non-URL) and three integration tests (breakdown values, CSV owner-only 403, CSV contents) - 38/38 passed at this milestone. Writing them exposed a real bug: the test database confused the by_day and by_hour queries because both start with the same words; the fix was test-side, and it is a good lesson in prefix matching. Try it: make a link, click it from two different apps and once by typing it directly, then open stats and inspect the downloaded CSV in a text editor, or import all spreadsheet columns explicitly as text. Explain back: why does SQL group by the raw referrer while host grouping happens in JavaScript?

9.3 Click-count limit (links that end)

A link meant for a limited audience - a hundred invites, a first-50 coupon - needs a click limit. max_clicks is an optional number set at creation (1 to 1,000,000). When the limit is reached, the short URL answers 410 Gone with a friendly "this link has ended" page instead of redirecting (410 is the same status expired links use: gone for good). Two terms carry this whole feature. A race condition: two requests doing read-decide-write at the same time can both read the old value and both decide "allowed" - the outcome depends on timing, not logic. Atomic: an operation the database performs as one indivisible step, so no other request can slip into its middle.

The first version of the gate was racy in exactly that way: SELECT COUNT(*) FROM clicks, then compare in JavaScript. Ten simultaneous visitors near the limit could all read 1, all pass, and a 2-click link would redirect ten times. The fix makes the database check and increment in a single statement:

UPDATE links SET clicks_used = clicks_used + 1

WHERE code = ? AND clicks_used < max_clicks

RETURNING clicks_used

This conditional UPDATE is one atomic database statement. If the limit is already reached, the WHERE matches no row, nothing is incremented, and the empty answer means "ended". RETURNING is a SQL clause that hands back the changed row, so the same statement can also report what it did. Live-verified: 10 parallel requests to a 2-click link produced exactly 2 redirects and 8 ended pages. Honest detail: clicks_used is the gate; the clicks table stays the analytics source, and if asynchronous click logging fails after the gate passes, the counts can drift - the gate errs toward ending on time, while analytics stay approximate as always. Visits past the end are deliberately not logged as clicks, since they never redirected.

Limited links skip the edge cache entirely, same as expiring links: a cached 302 could keep redirecting after the end for up to 60 seconds. The cost is a database read and, while admission remains available, a conditional counter update on each visit to such a link - that trade-off is part of section 10. Alternatives considered: counting the clicks table per visit (the racy first version), a Durable Object counter (Cloudflare's strongly-consistent worker object - the right tool, but new machinery for one counter), and a multi-statement transaction (not used here; the single conditional UPDATE avoids needing a multi-step check-and-increment transaction). Tests: unit tests for the validation (0, negatives, fractions, huge values rejected) and four integration tests - 410 at the limit, never cached, visits past the end uncounted, and ten parallel requests yielding exactly two redirects. Try it: create a link with max clicks 2, open it in two browsers, then a third time, and read the ended page. Explain back: why is one UPDATE statement safe where SELECT-then-decide is not?

9.4 Personal API tokens

Scripts cannot click "Sign in with Clerk". An API token is a long random password for a program: mint one in the account area (signed in), and the script sends it as a bearer token - Authorization: Bearer us_... (bearer means whoever bears this string is let in, so guard it like a password). The Worker then treats the request as the token's owner: created links are owned, private stats readable.

Only the token's SHA-256 hash is stored. A hash is a fixed-length fingerprint, not encryption you can decrypt. SHA-256 is designed to make finding an input from its hash impractical. Why a fast hash here when human passwords need a slow password-hashing scheme? Entropy is the uncertainty in a random choice. A token made from 24 uniformly random bytes has 192 bits of entropy, or 2^192 possible values. Unlike human-chosen passwords, these are not a small dictionary of likely guesses. Stored hashes are not directly usable as bearer tokens, but this does not make every database leak harmless or protect a raw token copied from a browser, script or log. The raw token is returned once at creation. If lost, revoke and remint; if stolen, it works until revoked. Revocation deletes the database row, so subsequent lookups fail; a request already authenticated can still finish. A database lookup costs work on each authenticated call, but supports revocation without waiting for a self-contained signed token to expire.

The flow: POST /api/tokens requires a valid owner credential, normally the signed-in Clerk session; an existing personal token can also authenticate this endpoint. crypto.getRandomValues fills 24 random bytes. Mapping each byte to two hexadecimal characters produces us_ plus 48 hex characters. SHA-256 is computed with WebCrypto, the browser/Worker cryptography API; only that hash, owner ID, name and timestamps go into api_tokens. The raw token is returned once. On a later API request, verifySessionUser checks the Bearer prefix and chooses personal-token lookup for a us_ value; otherwise it tries Clerk JWT verification. The shortened lookup excerpt below omits the surrounding request parsing and last-used timestamp update:

const hash = await sha256Hex(token); // excerpt: hash the supplied token

const row = await env.DB.prepare(

  "SELECT owner_id FROM api_tokens WHERE token_hash = ?").bind(hash).first();

One deliberate rule shipped the same hour (commit ee06426): a request that supplies a credential which fails to verify - revoked, mistyped, expired - gets 401, never a silent downgrade. The earlier behavior created a public anonymous link the caller believed was theirs: a surprising, unsafe ownership downgrade. Anonymous creation is for requests with no nonempty Authorization value. Any nonempty supplied value that fails verification is rejected. Two honest limits: last_used_at is best-effort (updated after the answer starts), and a token carries the owner's full power on this API - no narrower scopes yet.

Tests in tests/ownership.test.mjs cover minting without auth (401), owned creation and private stats, invalid/revoked token rejection without creating a link, token listing scoped to the owner with no raw token or hash, cross-owner revoke rejection, and token authentication without Clerk configured. These run against a test database stub, not production D1; the live checks reported separately confirm the deployed mint/create/revoke behavior. The hash lookup excerpt uses prepare for a parameterized SQL statement, bind(hash) to supply data without building SQL from the token, and first() to fetch one matching owner row. No row means authentication failed. Alternative designs include narrow per-token scopes and explicit expiry; neither is implemented. last_used_at is best-effort and not updated on every endpoint, so it is not an audit trail. A token currently grants the owner's full API access, including managing tokens. Try it with the two commands below using your own newly minted token; replace YOUR_TOKEN, never paste it into this document or commit it. A successful create returns owned: true. Revoke in the UI, rerun, and expect 401. Explain back: why store a hash, why can an existing token mint another, and why must invalid credentials not become anonymous access?

curl -X POST https://url-shortener.2wf0w2.workers.dev/api/links -H "Content-Type: application/json" -H "Authorization: Bearer YOUR_TOKEN" -d '{"url":"https://example.com"}'

curl https://url-shortener.2wf0w2.workers.dev/api/tokens -H "Authorization: Bearer YOUR_TOKEN"

10. Scaling - honest limits and the documented next step

The mentor question: how would this handle lakhs of users? First, translate users into requests, because registered accounts do not load a system - traffic does. Worked numbers: a lakh of people (100,000) each shortening one link on one day is 100,000 create requests plus their later clicks - already the size of the free plan's entire daily request allowance (100,000 requests/day), before any other project on the same account. A single popular link taking a lakh of clicks in a day is another 100,000 requests, mostly reads. So even modest adoption sits within sight of plan limits. Nothing here has been load-tested, and this section makes no capacity promises - it maps where the walls are. The figures come from the official pages, checked 12 Nov 2026: https://developers.cloudflare.com/workers/platform/limits/, https://developers.cloudflare.com/d1/platform/limits/, and https://clerk.com/pricing. They change over time - trust the pages, not this paragraph.

The Worker is stateless: it keeps no durable per-user state in one running process. Cloudflare can run requests across its network, and eligible repeated redirects can use an edge cache near visitors. This does not eliminate the shared database bottleneck. The cache is best-effort, not a guarantee: entries can be evicted early and several misses can overlap, so the database must still tolerate the full flow.

The real ceilings - which one bites first depends on the traffic shape, so treat this as a map, not a ranking. (1) The free Workers plan has a 100,000-request daily allowance; a burst, one unusually hot link, or storage growth can hurt earlier. (2) D1 is a single-region SQLite database: one primary is responsible for the writes, and this implementation uses D1 for creates, click logs, uncached link lookups and stats queries. The free tier allows 10 databases, 500 MB per database, 5 GB total, and at most 50 read subrequests per request. Per-click logging is the highest-volume write path. (3) Stats queries scan the clicks table per link - potentially expensive for popular links; the size threshold has not been measured. (4) Accounts: the current Clerk instance is a development one capped at 100 users. The production Hobby tier is free with 50,000 monthly retained users per app (https://clerk.com/pricing, 12 Nov 2026); moving instances is configuration, not new code.

Documented next step, deliberately NOT built: queue or buffer the click logging and roll clicks into daily summary rows, so the hot path stops writing one row per click; plus a Clerk production instance when real users arrive. That is where this project stops: the limits are named honestly, the path past them is written down, and no unneeded infrastructure was added.
